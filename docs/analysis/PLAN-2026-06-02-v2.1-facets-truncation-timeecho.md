## Workflow 编排设计（为何这样分组）

**关键结论：本轮三个 issue 的影响文件集两两不相交，可三 agent 全并行。** 这与上一批「logs.js/fields.js 热点需串行」不同——本轮 S1 改 `stores/fields.js`，D49 改 `stores/logs.js`（不同文件！`api/logs.js` 是 API 层、`stores/logs.js` 是 store 层，S1 用前者、D49 用后者），D22 改 `stores/query.js`，互不重叠；测试文件也各自独立（`fieldStore`/`searchOrchestration` vs `logsStore` vs `queryStore`）。

- **阶段 A — 三 agent 并行编码**：S1 / D49 / D22 各自「只改本 issue 文件、自验、**不动 git**」，并回报精确文件路径清单。
- **阶段 A‑commit — 串行提交**：按各 agent 回报路径，逐个 `git add <paths> && git commit`（git 操作串行化，规避索引锁竞争）。提交顺序 S1 → D49 → D22。
- **阶段 B — 收尾验证**：单独 agent 跑 `node --test` 全量 + `npm run lint` + `vite build`，回报 pass/fail；失败的 issue 标 ❌ 待人工。

> 所有 agent 遵守：**外科手术式改动**，只动与本 issue 直接相关的行；匹配既有风格（Vue3 `<script setup>` + Pinia setup store + Arco + `node:test`）；不顺手「改进」无关代码；不重排存量（ESLint 为 warn 级接入）。

## 各 Issue 详细规格

### S1 — facets 批量分布 🔴（M）

**根因 / 现状**：
- `src/api/logs.js:89` 已实现 `queryFacets({query, start, end, limit, maxValuesPerField})`（POST `/select/logsql/facets`），但**全仓无任何调用方**（`grep queryFacets src` 只命中定义与默认导出）。
- 字段侧栏每个 `FieldItem` 展开时各自 `loadFieldValues` 走 `/select/logsql/field_values` 单字段往返；Q2 之后，缺逐值计数的字段显示「分布未知」。facets 一次请求即可返回**多字段的高频值 + 真实 hits**，正是补这块拼图。

**做法**：
1. **`src/stores/fields.js` 新增 `loadFacets({ query, start, end })` action**：
   - 调 `queryFacets({ query, start, end, maxValuesPerField: 30 })`（`maxValuesPerField` 由 20 提到 **30**，与单字段路径 `limit: 30` 对齐，避免 facets 只给 20 个值而单字段给 30 个的口径割裂）。
   - **防御式归一化**（应对官方已知 bug：facets 的 `hits` 可能返回字符串、cluster 版历史上有 field/hits 交换）：对响应 `facets[]`（形如 `{ field_name, values:[{ field_value, hits }] }`，字段命名以实际后端为准）逐项 `Number(hits) || 0` 强转，过滤 NaN；`field_value` 缺失则跳过。无法解析的整体响应 → 静默不写缓存（保留既有 `loadFieldValues` 兜底），`logger.debug` 留痕。
   - **缓存键必须与 `FieldItem` 对齐（本 issue 的成败点）**：`FieldItem` 读 `getCachedValues({ field, isStream, query: effectiveQuery, start: timeRange.start, end: timeRange.end, filter: '' })`。因此 `loadFacets` 对每个返回字段，用**完全相同的** `query/start/end`（即 orchestration 透传的 `params.start/params.end` —— 已验证 = `queryStore.timeRange.start/end` 同一组令牌，如 `'1h'`/`'now'`）+ `filter: ''` 调 `createFieldValueCacheKey(...)` 写入 `fieldValuesCache.value[key]`。
   - **stream/log 分类**：facets 不区分 stream/log 字段，而缓存键含该维度。按 store 已有的 `streamFieldNames`/`logFieldNames` 名单判定每个 facet 字段的 `isStream`（命中 stream 名单则 `true`，否则 `false`/log）。因此 `loadFacets` 需在 `loadFieldNames` **之后**执行（见 orchestration 改动），保证名单已就位；对不在任一名单的字段按 log 处理。
   - 写入的缓存项：`{ values: 排序后[{value, hits}], total: Σhits, countsKnown: true, status: 'success', loading: false, error: null }`，并同步 `lastSuccessfulValuesByBaseKey[baseKey]`（与 `loadFieldValues` 成功路径一致），形态完全复用 `createEmptyFieldValueState` + 现有结构，使 `FieldItem` 的 `countsKnown` 分支直接画出真实分布条。
   - 注意 `values` 元素字段名要与 `FieldItem` 一致：`{ value, hits }`（facets 的 `field_value` → `value`）。
2. **`src/utils/searchOrchestration.js`**：`createSearchExecutor` 增加注入参数 `loadFacets`；在 `runAuxiliary` 内，于 `loadFieldNames` 成功**之后**追加 `loadFacets({ query, start, end })`（同一 `runId` 守卫；`Promise.allSettled` 或顺序 await 均可，但 facets 依赖 names 先就位 → 用 `await loadFieldNames(...).then(() => loadFacets(...))` 串在 names 之后，histogram 仍并行）。`loadFacets` 失败走 `onAuxiliaryError('facets', error)`，不影响主查询。保持向后兼容：`loadFacets` 缺省为 `() => {}`，旧测试不破。
3. **`src/App.vue`**：在 `createSearchExecutor({...})`（约 126 行）补一行 `loadFacets: (params) => fieldStore.loadFacets(params)`。
4. **`src/components/FieldItem.vue` / `FieldSidebar.vue`**：**预期无需改动**（缓存键对齐后，现有 `cachedData`/`countsKnown`/`getBarWidth` 渲染逻辑自动消费 facets 数据）。agent 须实测确认；若展开态首帧拿不到缓存，仅可加最小的「命中缓存即用、否则照旧 `loadValues`」守卫，不得重构。

**验收**：
- 新增 `loadFacets` 单测覆盖：① 正常响应 → 多字段缓存按对齐键写入、`countsKnown:true`、hits 为数字；② `hits` 为字符串 → 被 `Number()` 归一；③ 空/畸形响应 → 不抛、不污染缓存；④ stream 字段按名单分类到 `'stream'` 键。
- `searchOrchestration.test.mjs`：注入 mock `loadFacets`，断言一次 `execute` 后被调用一次、在 `loadFieldNames` 之后、`runId` 失效时不调用。
- 既有 `fieldStore`/`searchOrchestration` 测试不回归；`node --test` 全绿。
- 手动口径：展开一个原本「分布未知」的字段，现显示真实分布条（依赖后端返回逐值计数）。

**影响文件**：`src/stores/fields.js`、`src/utils/searchOrchestration.js`、`src/App.vue`、（按需）`src/api/logs.js`（仅在需微调 `queryFacets` 默认值时）、`src/components/FieldItem.vue`、`src/__tests__/fieldStore.test.mjs`、`src/__tests__/searchOrchestration.test.mjs`

**Commit**：`feat(fields): wire facets endpoint to batch-fill field value distributions (S1)`

### D49 — 超限截断可见提示 🟠（S）

**根因 / 现状**：
- Q2 已拆出 `logsStore.totalHits`（histogram 聚合的真实命中总数）与 `logsStore.loadedCount`（实际拉取条数，受 `settingsStore.resultLimit` 默认 500 截断）。`HitsHistogram.vue:6` 已显示「共命中 N · 已加载 M」，但**没有任何「已截断」的显式语义**——用户仍可能误以为 M 即全部。

**做法**：
1. **`src/stores/logs.js` 新增 computed/getter `isTruncated`**：`computed(() => totalHits.value > 0 && loadedCount.value > 0 && totalHits.value > loadedCount.value)`。用 `totalHits > loadedCount`（而非耦合 `resultLimit` 相等判断）作为「结果被截断」的权威信号，更稳健；在 return 中导出。
2. **`src/components/HitsHistogram.vue`**：在既有计数行（第 6 行）后，当 `logStore.isTruncated` 为真时追加一个**语义化警示徽标**，如：`⚠ 已截断 · 仅展示前 {loadedCount} / 共 {totalHits} 条`，配 `var(--warning)`/既有告警色与 `title` 说明「可缩小时间范围或提高结果上限以查看更多」。纯展示，不引新依赖；用现有 `formatNumber`。
3. 保持现有「共命中/已加载」文案不变，徽标作为附加项。

**验收**：
- `logsStore.test.mjs` 增断言：`totalHits=1000, loadedCount=500 → isTruncated=true`；`totalHits=loadedCount → false`；`totalHits=0` 或 `loadedCount=0 → false`。
- `node --test` 全绿；徽标仅在截断时出现。

**影响文件**：`src/stores/logs.js`、`src/components/HitsHistogram.vue`、`src/__tests__/logsStore.test.mjs`

**Commit**：`feat(ux): surface explicit truncation badge when total hits exceed loaded count (D49)`

### D22 — 自定义时间回显 + 相对/绝对区分 🟠（M）

**根因 / 现状**：
- `TimeRangePicker.vue` 的 `startTime`/`endTime` 是**初始为空、永不与 store 同步**的本地 ref：直方图刷选 `setCustomTime(...)` 后选择器不回填；自定义区间一旦选定，UI 上只有「自定义」字样，**不回显实际区间**，也无相对/绝对模式区分。
- `queryStore`：preset 用相对令牌（`start:'1h', end:'now'`），custom 用 ISO；`timePreset===''` 即处于自定义态。

**做法**：
1. **`src/stores/query.js` 新增只读派生**（供回显，避免在组件里重复判断）：
   - `isCustomTime = computed(() => !!(customStart.value && customEnd.value) && !timePreset.value)`。
   - `timeRangeLabel = computed(...)`：自定义态返回「`formatTimestamp(customStart) ~ formatTimestamp(customEnd)`」；预设态返回该 preset 的可读 label（如「最近 6h」）。复用 `utils/timeUtils.js` 的 `formatTimestamp`。导出二者。
2. **`src/components/TimeRangePicker.vue`**：
   - **回填**：用 `watch(() => [queryStore.customStart, queryStore.customEnd], ...)`（`immediate`）把 store 的 ISO 同步进 `startTime`/`endTime`，使再次打开 popover 时反显当前区间，并接住直方图刷选写入的 custom 值。
   - **回显**：把「自定义」按钮在 `queryStore.isCustomTime` 为真时显示为 `queryStore.timeRangeLabel`（或在其右侧加一段只读区间文本），`active` 高亮；预设态维持原样。
   - **相对/绝对语义**：在 popover 内顶部加一行说明「绝对时间区间」，与预设（相对）形成对照；预设按钮区即「相对」。不引入新状态机，仅靠 `isCustomTime` 区分两类。
   - 保留 `onCustomChange` 现有逻辑与自动刷新下拉不动。
3. 不改 `executeSearch` 触发链（App.vue 已 watch `customStart/customEnd`，回填不应反向触发新查询——`watch` 只单向 store→本地 ref，不在 watch 里调 `setCustomTime`，避免环）。

**验收**：
- `queryStore.test.mjs` 增断言：`setCustomTime(a,b)` 后 `isCustomTime===true` 且 `timeRangeLabel` 含两端时间；`setTimePreset('6h')` 后 `isCustomTime===false` 且 label 为预设可读名；切回预设清空 custom。
- `node --test` 全绿；手动：刷选直方图 → 打开自定义 popover 见区间已回填；自定义按钮回显当前区间。

**影响文件**：`src/stores/query.js`、`src/components/TimeRangePicker.vue`、`src/__tests__/queryStore.test.mjs`、（按需）`src/utils/timeUtils.js`（仅当 label 需新 helper）

**Commit**：`feat(ux): echo active time range and prefill custom pickers with relative/absolute distinction (D22)`
